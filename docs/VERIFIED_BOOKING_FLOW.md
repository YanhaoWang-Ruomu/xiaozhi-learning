# 可核验的演示预约流程

## 本次解决的问题

旧版本即使限制可用工具，仍可能跳过查询、输出未经核实的余量，或在没有明确选择时创建草稿。现在为有明确边界的演示预约增加程序执行路径：解析原始需求，查询实际排班，核对选择，调用实际草稿工具，按工具结果生成纯文本回复。普通问答继续由 LangChain4j 和 Qwen 处理。

这是一条确定性的业务流程，不是通用语义 Agent，也不是 Qwen 工具选择能力的提升。接口、会话记忆和 AI Services 工具循环仍使用 LangChain4j。没有替换预约最终确认页面。

## 执行与边界

- KnowledgeRetrievalAugmentor 在添加检索资料之前保存原始消息。一次性随机标记通过 UserMessage.name 绑定本轮，资料正文不能伪造该结构化字段。发送给 Qwen 的视图移除这一内部标记。
- BookingTurn 只识别有限中文表达：DEMO 编号或 UNKNOWN、内科、明确日期或今天/明天/后天/大后天、实际查询结果中的医生名，以及上午/下午或完整起止时间。相对日期在本轮按上海时区固定。
- 缺少医生或时段、要求代选、否定或不确定表达、日期冲突、矛盾或倒置时间均不能授权草稿。单个可用场次也不等于已经选择。
- “同一位”“刚才”等表达只能从相邻且有效的原始需求继承信息；否定、冲突或不属于预约流程的上一轮不能提供选择。仍需本轮重新查询。
- VerifiedBookingModels 在同步和流式入口产生实际工具请求，由 AI Services 执行。查询失败、满额或缺少排班时停止；未放号但有余量可以准备草稿，仍不能确认。
- AppointmentTools 在写入前独立校验一次性凭据、当前余量及原始需求中的选择。即使回退模型传入猜测参数，也不能靠凭据绕过明确选择。
- 回复只展示查询或保存结果中的日期、医生、时段和状态；内部凭据、场次编号、工具名不放入回复。草稿不占号，最终确认与取消继续通过网页的独立操作。
- 流式预约回复一次发送完整文本；这是服务器生成的片段，不是模型逐 token 生成。普通问答仍保留真实模型流式回调。

上下文是单进程内存状态：初始有效期五分钟，成功签发查询凭据后为九十秒；每轮替换旧标记，凭据只消费一次。重启、过期或切换实例后需要重新提供需求。尚未实现跨实例共享。症状或引述类表达回退模型，少量关键词不是急症识别系统；未识别的表达可能需要完整重述，不能宣称覆盖任意自然语言。

## 验证方式

新增 VerifiedBookingModelsTest 27 项，AppointmentToolFailureTest 增加 4 项；完整后端 223 项通过。覆盖真实调用前的选择条件、旧结果隔离、资料注入、错误、改时段、否定继承、时间矛盾，以及同步/流式分支。CI 检查测试数与零跳过。

真实数据库评测仍使用原六组十一轮及原判分规则。报告增加 selectedRoute，区分 SERVER_BOOKING_FLOW 与 MODEL。每次十轮走程序预约，一轮资料注入问答调用 Qwen；前者记录的模型 token 为零，但生产环境原有检索仍执行，不能解释成整个请求零成本。不要把总通过率写成六组模型推理通过率。

结果与报告见 [AGENT_MULTITURN_EVALS.md](AGENT_MULTITURN_EVALS.md)。真实医院、开放语言理解、通用事实核验、浏览器断网与云端取消均不在本次验收范围。
